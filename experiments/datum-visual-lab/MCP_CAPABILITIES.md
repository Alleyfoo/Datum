# MCP interaction and rendering capabilities

Research date: 27 October 2026. This document separates protocol guarantees, host/browser behavior and observations from this local experiment. The relevant core MCP revision is [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28); the dated [MCP Apps specification 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) identifies itself as stable. The Apps repository also contains a separate [draft](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx), which is not a promise of support. The tested Python SDK and reference host may negotiate an older core protocol; the Apps `ui/initialize` view-to-host handshake is separate from core MCP versioning. In core 2026-07-28, version and client capabilities travel with each request; older core revisions use an `initialize` handshake and session. See [versioning and compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning).

## Protocol and capability map

“Protocol” describes what an implementation may provide; it does not assert that every host renders or permits it. “Baseline” refers to the original `datum_visualize` implementation at commit `38a1cd3`; the experiment added in this session is described under the observations below.

| Capability | Mechanism and host requirements | Datum baseline at `38a1cd3` |
| --- | --- | --- |
| Text, images, structured data | Core tool results contain `content` blocks, including text, base64 image/audio, resource links or embedded resources, and may include `structuredContent` plus an output schema. Host decides presentation. In 2026-07-28 structured content can be any JSON value; an object is portable to earlier revisions. [Core tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools). | Text summary and structured object; no tool image/audio demonstration. |
| MCP Apps | A tool's `_meta.ui.resourceUri` references a predeclared `ui://` resource with MIME type `text/html;profile=mcp-app`. An Apps-capable host reads it and renders sandboxed HTML. Host may prefetch or cache the resource. [Apps specification](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx). | Reference host rendered the local resource; offline HTML is a separate mode. |
| App-only tools | `_meta.ui.visibility: ["app"]` makes a compliant host hide the tool from the model while allowing the app on the same server connection to call it. The host must reject app calls to tools lacking app visibility; default visibility is both model and app. Visibility is a routing rule, not server-side authentication or authorization. [Visibility](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx#resource-discovery). | The scenario call uses the model-and-app-visible `datum_visualize`; no app-only action. |
| Menus, buttons, forms, selections | HTML and JavaScript implement controls. The host renders the resource and can proxy `tools/call` from the app, if it exposes `serverTools` and permits the request. Menu schemas and business actions are application contracts, not a prescribed MCP widget language. A server must independently validate inputs and allowed actions. | Controls are hardcoded into the template; scenario calls fetch fresh data through the host. |
| Alternative host-owned input | Core [elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) requests user data through a capable client using form or URL mode; users can decline or cancel. In core 2026, the server returns `input_required` in the multi-round-trip flow. Forms owned by an MCP App do not require elicitation, but remain subject to host restrictions. | Not implemented or tested. |
| HTML, CSS, SVG | The Apps resource is HTML; its browser engine interprets inline HTML/CSS/SVG. Availability and fidelity depend on the host's browser, CSP, sizing and accessibility implementation. The specification does not guarantee particular browser APIs or visuals. | HTML/CSS and an interactive SVG evidence graph rendered in the reference host; zoom and node selection were checked. |
| Canvas and WebGL | Browser APIs usable by HTML when the embedded browser and policy permit them; they are not separate MCP rendering primitives. WebGL can fail or be software-rendered because of browser, hardware, drivers or policy. Detect support and handle failure. | Not tested at baseline. |
| Resizing | `HostContext.containerDimensions` describes fixed/flexible bounds; a view sends `ui/notifications/size-changed` for flexible dimensions. The Apps SDK can do this with `ResizeObserver`; a host should notify changed context. [Apps sizing](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx#container-dimensions). | No explicit size-change notifications or host-context handling. |
| Fullscreen and other display modes | View declares supported modes in `appCapabilities.availableDisplayModes`, checks `hostContext.availableDisplayModes`, requests `ui/request-display-mode` and uses the actual returned mode. A host can decline. `fullscreen` is the host's display mode, not necessarily the browser Fullscreen API; `pip` is optional. [Apps display modes](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx#display-modes). | No app mode negotiation. |
| Dynamic data and bidirectional messages | The host sends `ui/notifications/tool-input`, `tool-result` or `tool-cancelled` after initialization; an app requests a fresh result using `tools/call`. `resources/read`, `ui/message`, `ui/update-model-context`, logging and host-context changes are other defined channels, subject to host capabilities and permissions. A direct app tool call does not inherently invoke a model. [Apps lifecycle](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx#lifecycle). | In-app scenario changes request the server and replace the view; no model required in the reference host. Model context updates, push/subscription behavior and resource reads from the view are not tested. |
| Permissions, sandbox and loading | `ui.csp` declares connect/resource/frame/base URI domains; the host enforces a restrictive CSP and may be stricter. Resource metadata can request camera, microphone, geolocation or clipboard-write, but permission is not guaranteed. Hosts may refuse tool calls or require user consent. The web-host design uses an intermediate sandbox on a different origin. [Security and sandbox](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx#security-implications). | Local HTML and data are bundled. The local reference-host launcher permits CORS only for port 8080 loopback origins. No external domains or device permissions are requested. |

The stable Apps specification lists externally embedded URL resources, multiple UI resources in one result, view-to-view messaging, persistent/restored view state and screenshot APIs as deferred or future work. A particular host can offer extra facilities, but those are not portable promises. Ordinary image content in a core tool result is not the same thing as an interactive Apps resource. Host-owned [elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) is another interaction path, subject to declared client support; it is not a guarantee of arbitrary custom UI.

## Direct app-to-server interaction

1. A user or host invokes a model-visible opening tool. The tool identifies the predeclared UI resource, and the host fetches and renders it. This initial choice can be made by a host UI or an assistant.
2. The view sends `ui/initialize`; the host returns capabilities and context, and the view signals `ui/notifications/initialized`. The host delivers the opening result, including server-defined data.
3. The user selects an enabled action in the rendered view. The view checks that the host exposes server-tool support, then sends a `tools/call` request through its host bridge for a same-server app-visible tool.
4. The host may allow, deny, or subject the request to its own consent policy. When allowed, it forwards the call to Python. Python validates the action and returns structured data; the view updates from that response. No additional language-model call is needed for this path.

This is control through a host-mediated channel: the server defines the returned action model and effects, while the HTML implements the rendering and the host retains control of execution, privacy and available capabilities. App-only metadata does not replace input validation or permissions enforced by the server.

## Local observations and screenshots

The tests ran on Windows 11 in headless Chrome, with Node 24.14.1, Python 3.12.14, Python MCP SDK 2.3.0 and official basic-host revision `07cda2513b0b691ac261ac69c856062c9afb2824`. The Python MCP client negotiated **core 2025-11-25**, not the current 2026 core; the UI uses Apps protocol **2026-01-26**. Results establish this combination only. No actual AI assistant was tested.

**Server-driven interaction: supported in this host.** `datum_open_interaction_lab` returns a Python-loaded menu; the HTML has no hardcoded business action list. The host tool selector omitted `datum_menu_action` and `datum_menu_refresh`, both marked app-only. An enabled button called the app-only action through the host and displayed its structured response. The disabled control was disabled, and separate server calls rejected disabled and unknown IDs. The test edited `interaction_menu.json`, refreshed through the app-only tool and clicked a newly added action; its result appeared without rebuilding or reloading the HTML. The test restored the file bytes. This path used the reference host and no LLM. Visibility is not access control: a direct protocol client could still call the listed server tool, so real authorization belongs on the server. See [menu screenshot](screenshots/interaction-menu.png) and [changed menu screenshot](screenshots/interaction-menu-changed.png).

**Rendering and display: supported in this host for the tested samples.** The probe rendered eight server-data SVG bars, a Canvas 2D drawing whose sampled pixel was `[121,174,242,255]`, and a 2,000-row HTML table. One synchronous DOM construction and draw measurement was 10 ms; it is not an end-to-end paint, responsiveness or scalability benchmark. The nonstandard Chrome heap estimate was 26,890,723 bytes for the page at one point, not total process memory or a reliable memory comparison. A WebGL context, clear and pixel read succeeded (`[51,178,102,255]`); this does not establish GPU hardware acceleration or broader WebGL support.

The host advertised `inline` and `fullscreen` and returned those modes when requested; this is host fullscreen, not a test of the browser Fullscreen API. A size notification requesting 700 px changed the outer frame from 400 to 706 px after the host animation settled; the outer frame includes the host border. At a 520 px outer viewport, the inner width was 480 px and the probe grid collapsed to one 460 px column. See [desktop](screenshots/rendering-probe-desktop.png), [host fullscreen](screenshots/rendering-probe-fullscreen.png), [narrow window](screenshots/rendering-probe-narrow.png) and [measurement JSON](screenshots/rendering-observations.json).

Both host tests reported no page errors and one generic console 404 whose URL and cause were not established. The host and server run on loopback; the CORS launcher permits the specified reference-host origins. The tests do not prove other hosts will grant tool calls, modes, rendering APIs, permission requests, downloads or external resource loads. No camera, microphone, clipboard, external CSP loading, browser-native fullscreen, offline network behavior, screen reader, longer stress test, higher row count or memory profiling was tested.

Run instructions and `tests/test_interaction_host.cjs` / `tests/test_rendering_host.cjs` are in [README.md](README.md). The interaction test temporarily edits its configuration, restores it in `finally`, and should run against a disposable copy without concurrent edits. The full suite has 17 passing Python tests; it requires the SDK because menu registration is included.

The earlier baseline run recorded live scenario results, graph zoom and node selection in the official host; the fixture change appeared without rebuilding HTML. It did not test Canvas, WebGL, fullscreen, app-only tools or an actual AI assistant. See [TEST_REPORT.md](TEST_REPORT.md) for baseline evidence.

## Host-specific boundaries and architecture recommendations

The pinned official [basic-host](https://github.com/modelcontextprotocol/ext-apps/tree/main/examples/basic-host) is a manual test client with a double-iframe sandbox, not an AI assistant. At revision `07cda2513b0b691ac261ac69c856062c9afb2824`, its implementation advertises inline/fullscreen, supplies a maximum flexible height and implements size-change and display-mode handlers. Its inner sandbox grants scripts, same-origin and forms; it does not grant downloads by default. Other hosts may behave differently. A tool call accepted here does not establish a different host's permissions, response timing or assistant tool-selection behavior.

Keep the deterministic Python domain engine independent of an application-specific presentation contract. Deliver a stable versioned HTML renderer as a `ui://` resource and send current, validated action descriptors and structured data as tool results; do not rebuild HTML for ordinary data or menu changes. Use app-only tools for direct, read-only interactions, validate enabled state server-side on every request, and handle disabled capabilities, errors, cancellation and stale responses explicitly. Supply useful core text results for non-Apps hosts. Inspect host-reported capabilities and actual mode, and use bounded datasets, pagination or virtualization for large views rather than assuming a sandbox has desktop-app resources. Keep the host's own permission decisions authoritative and test each intended host and browser independently. No ERP write-back or authorization workflow is implied by this experiment.
